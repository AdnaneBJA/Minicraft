# Load-testing bots in Go

## Goal
`loadtest/`, a Go tool that launches N bot players against a minicraft-server and measures what players feel:
- input latency;
- tick jitter;
- join time;
- throughput;
- failures;
- optionally, the server's CPU and memory.

It gives the project real performance numbers for the README and interviews, and finds the server's breaking point.

**What the user decided:**
- **Bot fleet in Go** (option 1 of the suggestions).
- **Local or throwaway servers only.** Production stays untouched: no bots in the live world, the stats or the 32 slots.
- **Approved design:**
  - §1: a protocol-level client, the metrics, and a CLI with a live line and a final report;
  - §2: the packages, the steady / ramp-to-failure / soak modes, and a safety guard for non-local URLs;
  - §3: tests (fixtures generated by the C++ side, a fake server, a CI end-to-end run), and results published in the README plus ADR 0004.

**Success criteria:**
1. `go run ./cmd/loadtest --url ws://localhost:7777 --bots 32 --duration 3m` runs, prints a live line each second and
   writes `report.md` and `report.json`.
2. Ramp mode finds and names the breaking point: the latency threshold, connection refusals, or the 32-player cap.
3. The Go protocol code decodes and re-encodes byte fixtures produced by the C++ protocol code, so a format change
   on either side fails CI.
4. CI runs a short end-to-end load test against the real server on every push.
5. The README's "Performance" section shows numbers measured with the tool on a t3.micro, and how to reproduce them.

## 1. The wire format (`loadtest/protocol`)
This mirrors `net-common/protocol.*` exactly:
- **Encoding:** little-endian `i32`/`u64`, `u8`, and strings as an `i32` length followed by the bytes.
- **Message:** the first byte is its type:
  - client → server: 0 Hello, 1 Input, 2 Command, 3 Chat, 4 StateHash;
  - server → client: 5 Welcome, 6 Joined, 7 Tick, 8 ChatLine, 9 Error.

| Message | Body |
|---|---|
| Hello | name |
| Input | keys as one byte: bit0 left, bit1 right, bit2 up, bit3 down, bit4 attack held, bit5 attack pressed |
| Chat | text (≤ 80) |
| Welcome | playerId i32 |
| Joined | seed i32, count i32, then that many ticks |
| Tick | tick i32, turn count i32, then turns: playerId i32, keys u8, command count i32, then commands (kind u8, a b c d i32, text) |
| ChatLine | from, text |
| Error | text (≤ 200) |

**Robustness:** the decoder never panics. Truncated input, negative or oversized counts, unknown types and trailing
bytes return errors, with the same limits as C++: names ≤ 12, at most 64 turns per tick, at most 18 commands per turn,
history ≤ 6 h of ticks.

**Fixtures:**
- A C++ program `protocol_fixtures` (a CMake target, native only) writes one `.bin` file per message, built from
  fixed example values, into `loadtest/protocol/testdata/`. The files are committed.
- The C++ test `ProtocolFixtures.MatchCommittedFiles` re-encodes the same examples and compares them with the
  committed files.
- The Go tests decode each file to the expected values and re-encode it byte-for-byte.

Either side changing the format breaks a test.

## 2. A bot (`loadtest/bot`)
- **Connecting:** each bot connects with `github.com/coder/websocket`, sends Hello(`bot%03d`), and waits for Welcome
  (its id) and Joined (history size, decode time).
- **Reading:** a reader goroutine decodes every message:
  - Tick: records the arrival time, and checks its own turn's keys against its pending key change;
  - ChatLine: counted;
  - Error: recorded; "Name already in use" is a join failure.
- **Acting:** an actor goroutine changes direction every 0.5–2 s (a random walk from a per-bot seeded RNG). It holds
  attack 20% of the time, with a press on each new attack, and sends chat every 20–60 s on average. It only sends
  Input when the keys change, as the real client does.
- **Input latency:** at a key change, the bot records `(newKeys, sentAt)`. The first Tick in which the bot's own turn
  carries `newKeys` closes the measurement: `now − sentAt`. If another change happens first, the pending one is
  dropped as superseded and not counted.
- **Tick jitter:** the gap between consecutive Ticks, minus 16.667 ms. The absolute value goes into a histogram.
  "Late bursts" counts ticks arriving under 2 ms after the previous one following a gap over 50 ms.
- **Ending:**
  - a dropped connection is recorded as a failure, and in steady mode the bot doesn't reconnect;
  - stopping closes the connection cleanly, so the server logs a normal leave.

## 3. Metrics, server sampling, reports
- **`metrics`:**
  - a lock-protected log-bucket histogram (1 µs to 60 s, about 1% resolution) that's safe to use concurrently, with
    p50, p95, p99, max and count;
  - atomic counters: bots connected, joins, join failures, drops, messages and bytes received, chat lines;
  - `Snapshot()` for the live line, with values over the last second.
- **`procstat` (optional, `--server-pid N`):** samples the process's CPU % and RSS once a second via
  `github.com/shirou/gopsutil/v4`, and reports their maximum and average.
- **`report`:**
  - live line: `t=00:42 bots=32/32 lat p50=21ms p99=48ms jitter p99=4ms rx=1.9 MB/s drops=0`;
  - `report.json`: the config, the duration, every histogram summary, the counters, the process stats, and for ramp
    mode the per-step results and the breaking point;
  - `report.md`: the same, formatted for pasting into the README.

## 4. The CLI (`loadtest/cmd/loadtest`)
**Flags:**
- `--url` (default `ws://localhost:7777`)
- `--bots` (default 8)
- `--ramp` (time to add all bots; default 10 s)
- `--duration` (default 1 min)
- `--mode` = `steady` | `ramp` | `soak`
- `--step` (4), `--every` (15 s), `--max-p99` (150 ms): ramp mode
- `--join-probe-every` (1 min): soak mode
- `--server-pid`
- `--out` (default `report`)
- `--seed`
- `--i-know-this-is-not-local`

**Modes:**
- **steady:** ramp up, hold, stop, report.
- **ramp:** add `step` bots every `every`. It stops at the first step where p99 input latency is over `max-p99`,
  where any connection is refused or dropped, or once the target `--bots` is reached. The breaking point (bots and
  cause) goes in the report.
- **soak:** steady, and every `join-probe-every` a fresh probe bot joins, measures its join time and leaves. The
  report shows how join time grows with the world's age.

**Safety:** unless `--i-know-this-is-not-local` is given, the tool refuses a URL whose host isn't `localhost`,
`127.0.0.1`, `::1` or a private (RFC 1918) address. A temporary EC2 instance is reached by its public IP, so it needs
the flag.

**Ctrl+C** stops the bots and still writes the report.

## 5. Tests and CI
- **`protocol`:** fixture decode and re-encode; round trips; malformed-input table tests (none panic).
- **`metrics`:** percentiles of known distributions within 2%; concurrent recording with `-race`.
- **`bot`, against a fake server (`internal/fakeserver`):**
  - Welcome, Joined, then 60 Hz ticks that echo each bot's latest keys, after an adjustable delay;
  - a join is counted;
  - input latency with a 50 ms delay measures 50–75 ms;
  - "Name already in use" is a join failure;
  - closing the server mid-run counts drops.
- **CLI:** the URL safety check, as table tests.
- **C++:** `ProtocolFixtures.MatchCommittedFiles` in `server_tests`.
- **CI, `tests.yml`:**
  - a `loadtest` job: `go vet`, `go test -race`;
  - then build `minicraft-server` (server-only CMake), start it, and run
    `go run ./cmd/loadtest --bots 8 --duration 20s --out ci-report`;
  - it fails if any join fails, any bot drops, or p99 input latency ≥ 250 ms (a generous CI bound);
  - the report is uploaded as an artifact.

## 6. Results and docs
- **Measured runs** (by the assistant, against a native local server):
  - steady 32 bots for 3 min;
  - ramp to 40, to show the 32-player cap.

  If the user launches a temporary t3.micro, the same runs there; results for each environment are labelled.
- **README:** a "Performance" section with a numbers table, the environment, and the commands to reproduce.
- **ADR 0004:** what lockstep input latency is made of (one round trip plus up to one tick of waiting), and the
  measured breakdown.
- **`loadtest/README.md`:** usage, modes, the safety flag, and how to run against a throwaway EC2 instance.

## Out of scope
- Bots running the real simulation.
- Load-testing production.
- Load generation spread over several machines.
- Metrics dashboards (a separate idea).
